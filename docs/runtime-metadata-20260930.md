# 程序元数据变化与内容一致性核验

## 已确认的触发机制

上一轮日志显示 `ecg_core.beat_editor` 只有 `ctime_ns` 改变，旧策略仍返回“软件文件已更新”的 409。此次在临时合成文件上执行 macOS `xattr -w`，复现 **只有 ctime 改变、文件 SHA-256 不变、旧运行保护拒绝**。这证实元数据操作可以引起一类误报，不能据此认定此前是哪个系统进程／同步程序改了属性；此前也没有记录当时的第二份内容摘要。

`ctime` 在该平台表示元数据变更时间，而不是内容版本或文件创建时间。[Python 官方 stat 说明](https://docs.python.org/3/library/os.html#os.stat_result.st_ctime_ns)区分了 mtime、ctime 与 birthtime，并说明跨平台语义差异。第一次复现实验尝试 `os.setxattr`，当前 Python 不提供该入口，未改变合成文件；改用本机 `/usr/bin/xattr` 完成。未改实际程序文件的属性。

## 新边界

`AnalysisRuntime` 在启动时保留各受监控文件原始内容摘要，并串行完成元数据恢复核验：

1. 元数据完全未变：沿用原快速检查，不重复读取全文。
2. **只有 ctime 变化**、设备号／inode／长度／mtime 都相同、已知启动摘要、此前未检测到更新：核对新签名对应的文件内容。读取前后及整组核验结束前都必须保持同一签名，字节长度和 SHA-256 必须与启动时一致。
3. 核验成功：仅更新已验证的元数据签名；程序构建标识和报告依据不变，不重新导入模块，不撤销医生审核。信息日志仅包含固定模块标签及内容一致结果，不包含路径、患者内容或原始异常文本。
4. 文件内容不同、mtime／长度／inode／设备变化、文件缺失、摘要未知、校验失败或竞争：继续拒绝。任一模块拒绝时不部分接纳其他模块的新签名。
5. 已检测到更新后，进程保持要求重启的状态；即使字节或所有元数据被恢复，也不自动恢复写入／导出。重复相同故障日志去重。日志写入失败不能绕过核验。

这不是忽略 ctime，也不允许热更新新算法。即使内容相同，只要 mtime 或 inode 改变，仍执行严格重启策略。原始病例 DATA／EBI／LPS 的哈希、缓存、审核失效规则没有改变。

## 仍未证明的事项

- 此前修改真实源码 ctime 的外部进程仍未确定；不能将新保护描述为已找到该进程或修复所有运行中断。
- 核验不是操作系统原子快照、代码签名或抵抗管理员攻击的机制。与原设计一样，仍需稳定、受控的安装目录；末次检查之后发生的外部写入不能彻底排除。
- 本轮只在当前 macOS / Python / Waitress 环境完成原生属性验证。跨平台测试有原生 xattr 条件跳过；当前完整回归运行在 macOS，没有因此跳过该项。
- 本轮不改 UI、诊断公式或设备标定，未重做浏览器视觉验收；不能据此宣称达到临床部署验收。
