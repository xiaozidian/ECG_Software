# 事件列表加速与修订一致性

日期：2026-09-29。范围为模板全部记录、报告事件列表的读取与分页，不是诊断算法准确率或整页波形加载速度证明。

## 确认的问题

此前一次回归的事件读取失败没有保存响应正文。此次用隔离数据库、只读的 10 例来源执行 50 次请求（10 次顺序冷读、两组各 20 次四线程请求），没有复现失败；三组最慢耗时分别约 1.385、5.169、5.014 秒。**未找到该偶发失败的根因，不将重试成功宣称为已修复。**

发现并处理两项明确的性能开销：

- 每次换页／切分类都重新物化全部修订心搏并构建全天事件索引。
- 每次显示 24 个小波形卡片，也先构造全天约 10 万个显示对象，再取当前页。

## 实现与安全边界

1. `ClinicalQueryCache` 在单个应用进程内复用事件列表私有索引，以病例、原始文件／分析构建依据、复核修订号为键。仅事件列表接口使用；报告统计、图条、PDF 和编辑写入路径仍独立构建。
2. 同键并发请求共享一次构建；不同键不持有全局计算锁。构建失败不缓存，等待超时返回可重试的 503，不返回旧数据、不取消或重复启动原构建。
3. 最多保留两个索引，结构权重不超过 300,000（心搏行数＋事件数＋目标心搏引用数）；超大索引只共享在途计算，不长期保留。此限制不是精确字节／RSS 上限，也不限制不同键的所有在途构建。
4. 原有来源结构校验、构建前后／查询后依据核对均保留。心搏修订、撤销、模板、节律、注释、患者资料、审核或 DATA／EBI／LPS 变化均改变复用键或拒绝请求。缓存命中不能掩盖来源损坏／缺失。
5. 查询只向 UI 返回当前投影的深复制，避免调用者修改缓存所有权内的对象。查询函数本身须保持只读。该机制不是文件系统原子快照。
6. Python 与浏览器实现均先筛选并排序原行引用，计算完整小时分布与总数后，再生成当前页的显示对象。保留半开时间区间、模板筛选、相同时刻排序、非 QRS 标记、诊断修订状态及 200 条上限。
7. 缓存实现已纳入后端分析构建指纹，更新后需重启。静态演示同步了查询算法；没有给浏览器虚构后端文件指纹。
